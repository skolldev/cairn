# Watcher coalesces through the Slot, not a debounce timer

The plan had the watcher wait for a 100–200 ms debounce before refreshing, using `notify-debouncer-full`. We dropped the timer. A trailing debounce adds its whole length to every External change, so it can't fit the 100 ms External change Budget at all, while the read itself measured about 25–30 ms on both OSes (#11). That figure was for a read scoped to the watcher's 10 changed paths. #40 found Cairn reading everything on every change instead, which on the Linux kernel is far slower, so a change at known worktree paths now reads only those (see below).

Instead of a timer, the first watcher event starts a refresh of the affected Slot straight away. Events that arrive while it runs leave one pending refresh in that Slot, which already holds at most one running and one pending Read Job. A burst, such as a checkout writing thousands of files, costs at most two refreshes back to back.

## Consequences

- An atomic editor save (a temp file, then a rename) can briefly show the intermediate state. The pending refresh corrects it one read later. We accept that.
- A refresh never Supersedes the running read, only the pending one: the running read's answer is newer than what is shown, so it still publishes. A stream of changes longer than one read, such as a build writing for minutes, then publishes once per read instead of nothing until it stops (#21). Only a new question, such as an Open, Supersedes and stops the running read.
- There is no tunable quiet window. If Phase 1 finds refresh storms anyway, the fix belongs in the Slot or in how events map to Slots, not in a timer in front of them.
- A change to a file git ignores and doesn't track refreshes nothing (#32): the watcher keeps gix's exclude stack and the index, and asks them per path. It rebuilds them, and refreshes status, when `index`, `.git/info/exclude`, `config` or any `.gitignore` changes. `core.excludesFile` and the global git config live outside the watched root, so a pattern removed there leaves matching changes skipped until the next rebuild or Open. We accept that. In a linked worktree or a submodule, whose `.git` is a file, the watcher watches the git dir and common dir it points to as well (#35), so the same holds there.
- A change the watcher saw only at worktree files reads only those files again (#40). Unstaged runs `git diff-files` on just those paths and keeps the rest of the list it read last. Untracked walks only the part of the worktree each path can affect: the child of the path's deepest ancestor that holds a tracked file, since only that can appear, vanish or collapse into `dir/`. Staged isn't read at all, because a worktree file can't change HEAD vs index. Anything else reads the whole list as before: an Open, a Local write Job, the index, HEAD, config, `info/exclude`, any `.gitignore` (for Untracked), more than 256 changed paths, a failed read, or an event the watcher lost. On the kernel on macOS (M3 Max) a saved tracked file's narrowed Unstaged read took 40–55 ms, about 13 ms of it `diff-files` and most of the rest starting git twice (`diff-files`, then `hash-object` for a stat-only candidate), and its narrowed Untracked read 24–36 ms, mostly loading the index. The full reads took 95–130 ms and 210–380 ms. A `git switch` still reads everything: it writes the index, and in the Budget harness it changes `.gitignore` too.
- A narrowed read trusts the watcher: a change the OS never reports, without flagging a rescan, stays unseen until something reads everything again, where before the next event's full read would have caught it. A read that fails, is stopped or panics hands its paths back as "read everything".
- A read takes the changed paths as it starts. One save often reports two events, so the read queued behind the first usually finds nothing left to read and answers from the last list at once.
